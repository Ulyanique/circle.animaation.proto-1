## 2. Безопасность: prototype pollution в разборе настроек (важно)

`deepMerge` в `src/config.js:354` рекурсивно обходит **ключи из внешнего JSON** и
пишет их в целевой объект. `JSON.parse` создаёт `__proto__` как собственный ключ
(`Object.keys` его видит), поэтому:

```js
// src/config.js:358 — if (!target[k] ...) target[k] = {} при k === "__proto__"
// это запись в прототип целевого объекта, а дальше deepMerge пишет уже в Object.prototype
```

Воспроизведено на текущем коде (временный скрипт, затем удалён):

```
mergeConfig(WAITING_DEFAULTS, {"__proto__": {"polluted": "YES"}})
  → ({}).polluted === "YES"          // загрязнён ОБЩИЙ Object.prototype
parseConfigJSON('{"__proto__":{"polluted2":"x"}}')  → ({}).polluted2 === "x"
```

Два реальных пути входа, оба достижимы без файла на диске:

1. **Ссылка** `#cfg=<base64url>` → `decodeConfigShareHash` (`src/scene-snapshots.js:101`)
   → `mergeConfig` в `src/main.js:59`. Достаточно, чтобы жертва открыла ссылку.
2. **Импорт JSON** сцены/проекта → `parseConfigJSON` (`src/config.js:510`) /
   `parseProjectJSON` (`:533`) → `mergeConfig`.

Почему это конкретно опасно именно здесь: конфиг сравнивается с умолчаниями через
`in` (например `src/ui.js:164` `if (!(f.key in current[section.id])) continue;`), а
`in` идёт по прототипу. Загрязнение прототипа может изменить поведение проверок
полей интерфейса и любых `obj[key] ?? fallback` по всему приложению. Это не RCE,
но недетерминированное поведение и потенциальный обход проверок.

**Правка на 3 строки** (проверена отдельным скриптом — легитимные ключи мержатся,
загрязнения нет):

```js
const UNSAFE_KEYS = new Set(["__proto__", "constructor", "prototype"]);
// в deepMerge:
for (const k of Object.keys(source)) {
  if (UNSAFE_KEYS.has(k)) continue;
  ...
  if (!Object.hasOwn(target, k) || ...) target[k] = {};   // вместо !target[k]
}
```

Затем — регрессионный тест: `mergeConfig(DEFAULTS, {"__proto__":{"x":1}})` не должен
менять `({}).x`. Дешёво, безопасно для совместимости старых JSON, закрывает все три
пути сразу.

## 3. Архитектура

### 3.1. Схема настроек не знает про сцену — знание размазано по UI

`SCHEMA` (`src/config.js:16`) — глобальный список на 246 полей и 8 секций. Какие
секции и поля показывать для конкретной сцены, решается **цепочкой `if` в одном
цикле** `src/ui.js:130–169`:

```js
if (editing === "partners" && !["partners", ...].includes(section.id)) continue;
if (!current[section.id] || (section.id === "caption" && editing === "photo-pause")) continue;
if (section.id === "typography" && ((editing === "brand" && /^(subtitle|date)/.test(f.key)) || ...)) continue;
if (section.id === "logo" && (editing === "waiting" || ...) && ...) continue;
if (section.id === "caption" && ((editing === "brand" && ...) || ...)) continue;
```

Последствия: добавить сцену или поле = править условие, а не объявить данные; легко
получить UI, который показывает несуществующее поле; `in`-проверка ещё и
чувствительна к загрязнению прототипа (§2). При этом у каждой сцены свой набор
ключей (`FINALE_DEFAULTS` вообще не содержит `partners`, у `PARTNERS_DEFAULTS` нет
`finale`) — то есть разделение уже есть в данных, но не в описании.

**Предложение.** Описать видимость данными рядом со схемой, например
`visibleFor: { scenes: ["brand","finale"], except: ["date*"] }` или
`SCENE_SECTIONS = { partners: ["partners","typography","timeline","playback","transition"], ... }`,
и оставить в `ui.js` один общий фильтр. `editor-properties.js:10` берёт `SCHEMA` так
же — выигрыш общий. Это рефакторинг без изменения поведения, его удобно закрыть
существующими проверками (`verify:settings`, `verify:editor:lite`).

### 3.2. `editor.js` — 1839 строк в одной функции

`createFrameEditor` (`src/editor.js:25`) — **одна функция на 1815 строк** с ~120
вложенными функциями и ~80 `querySelector` по разметке. Периферия уже вынесена в 16
модулей (`editor-timeline`, `editor-history`, `editor-math`, `editor-layers`…, ~178 КБ
суммарно), а внутри остались DOM-панели и проводка событий.

**Предложение (поэтапно, без «большого взрыва»):** вынести три независимых куска в
соседние модули по тому же принципу, что уже принят в проекте:
1. панель слоёв (список, поиск, фильтр, кнопки видимости/блокировки);
2. инспектор (создание полей + чтение/запись значений);
3. таймлайн-взаимодействие (drag краёв, курсор, фазы).

Каждый шаг — отдельная проверка в `verify:editor:lite`, которая уже есть. Критерий
успеха: `editor.js` < ~800 строк, поведение и горячие клавиши не меняются.

### 3.3. Условные ограничения не описаны как данные

То же, что §3.1, но про лимиты: где-то в коде зашиты проверки диапазона, где-то —
`min/max/step` в схеме. Стоит держать один источник для «поле валидно для сцены X»
(схема + валидатор), чтобы импорт, редактор и панель не расходились.

## 4. Тестирование

Покрытие хорошее, но есть перекос: густо покрыта чистая логика, почти не покрыты
«зеркала» и связующие модули. Ниже — по убыванию риска.

| Модуль | Строк | Покрытие строк | Почему важно |
|---|---|---|---|
| `src/caption-compositor.js` | 286 | **10 %** | Второй (canvas) рендерер титров — дублирует DOM. Расхождение предпросмотра и экспорта = брак в MP4. Тестом покрыта только `transformGlyph`, а `lineBaseline` и `drawCaption` — нет |
| `src/caption-content.js` | 97 | **10 %** | Тот же риск расхождения текста/регистра |
| `src/caption-fit.js` | — | **31 %** | Автоподгонка в DOM и в canvas должна совпадать |
| `src/operator.js` | 250 | **7 %** | Пульт, seek, переключение режимов (браузерная проверка `verify:operator` есть, юнит-тестов нет) |
| `src/review.js` | 108 | **18 %** | Мёртвый код (§5), но `reviewMarkers` тестируется |
| `src/partners-graphics.js` | 141 | **37 %** | Canvas-макет спонсоров без юнит-тестов |
| `src/sparks.js`, `src/fx.js` | — | 59 % / 54 % | WebGL-часть, частично оправдано |

**Предложение.** Приоритет — чистые функции «зеркал»: разложить
`caption-compositor` на «что рисовать» (позиции, кегль, трекинг, прозрачность по
графемам — чистая функция) и «как рисовать» (ctx-вызовы). Первую часть покрыть
юнит-тестами и сравнением с тем же расчётом для DOM. Это единственное место, где
ошибка напрямую портит экспортный файл, а не только предпросмотр.

## 5. Мёртвый код и неиспользуемые экспорты (дешёвая уборка)

Проверено перебором экспортов по `src/`, `scripts/`, `tests/`:

## 6. Надёжность и эксплуатация

### 6.1. CI описан, но не включён

`docs/ci-checks.yml` содержит корректный workflow (`npm ci → test → typecheck →
build`), а каталога `.github/` в репозитории **нет**. README (§23) это честно
оговаривает, но фактически проверки при пуше не запускаются.

**Предложение.** Перенести файл в `.github/workflows/checks.yml` (нужен
`workflows`-скоуп). Заодно добавить в него `npm audit --omit=dev` (сейчас 0
уязвимостей — хорошая база) и кэш `~/.cache/headless`, если когда-нибудь захочется
браузерные проверки.

### 6.2. `npm audit`: 9 high — только dev-цепочка Puppeteer

Все они в `puppeteer-core@23 → @puppeteer/browsers → proxy-agent → basic-ftp/zod/
extract-zip`. В продакшн-бандл не попадают (`--omit=dev` → 0). `npm audit fix --force`
предлагает `puppeteer-core@25` — **мажор**, и он сломает `scripts/browser.cjs`
(используется всеми 40 `verify:*`). Если обновляться — отдельной задачей, с прогоном
`verify:render` и `verify:loader` на новой версии; не «заодно».

### 6.3. Вес первой загрузки

`dist/index.html` преload'ит **все** вендорные чанки, включая тяжёлые:

```
vendor-three      812 КБ (239 КБ gzip)
vendor-mediabunny 527 КБ (135 КБ gzip)   ← нужен только для экспорта MP4
vendor-opentype   243 КБ (68 КБ gzip)
main              331 КБ (105 КБ gzip)
```

Итого ~1.9 МБ JS (≈550 КБ gzip) до первого кадра. Для «заставки на большом экране»
это терпимо, но загрузчик обещает быстрый старт. `mediabunny` и редактор нужны
только по кнопке «Записать»/«Редактировать» — их логично грузить динамическим
`import()` по требованию (в коде уже есть примеры такого подхода в `verify-*.cjs`).
Эффект: минус ~135 КБ gzip с критического пути без изменения функциональности.
Three.js трогать не нужно — он нужен сразу.

### 6.4. Производительность никто не сторожит

`scripts/benchmark-render.cjs` умеет мерить медиану кадра по ширинам и честно
оговаривает, что измерения синтетические. Но это ручной скрипт: ни одна проверка не
падает, если кадр стал вдвое дороже. Для заставки, которая должна держать 60 fps на
слабой площадке, имеет смысл дешёвый «сторож»: в `verify:render` дополнительно
замерять медиану кадра своей сцены и сравнивать с сохранённым эталоном с
допуском (например, +40 %). Достаточно одного числа в `docs/`, чтобы правка
постобработки не уронила плавность незаметно.

### 6.5. Документация

`README.md` — 515 строк, но строки 377 (4123 символа), 515 (1629), 177 (1228) и 29
(1271) — «простыни», которые тяжело ревьюить и диффить. `docs/` — 3.8 МБ, из них
3.6 МБ — скриншоты.
Предложение: разбить самые длинные абзацы README на списки/подзаголовки; тяжёлые
изображения аудита держать вне git (артефакт прогона), а в `docs/` — 2–3 ключевых.

### 6.6. Доступность

`prefers-reduced-motion` учтён только для экрана загрузки (`index.html`), а панели,
тосты и переходы в `styles.css` его игнорируют. Для заставки это осознанный выбор,
но для интерфейса редактора (кто-то монтирует с ноутбука) можно добавить
`@media (prefers-reduced-motion: reduce)` для панелей/анимаций интерфейса — не для
сцены. Фокус-стили есть (37 правил `:focus`) — это хорошо.
